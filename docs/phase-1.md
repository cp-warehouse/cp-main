# Phase 1 — 조사 과정과 설계 결정

목표: 서로 다른 기업 데이터를 같은 기업에 연결하고, 출처를 확인할 수 있는 첫 적재 기반 확보.

## 여기까지의 과정

| 기록 | 검토 내용 | 이번 구현과의 연결 |
|---|---|---|
| 서비스 1차 설계 | 기업의 상태와 개발자 입사 준비에 필요한 질문 정의 | 출처·시점이 있는 기업 분석을 서비스 목표로 설정 |
| 수집·적재 조사 | 기업·제품·재무·채용·기술·사건·시장, 7개 데이터 영역 검토 | 전체 수집 범위와 첫 구현 범위의 구분 |
| DB 학습·적재 검토 | RDB·검색·Vector·Graph의 역할 비교 | 구조화된 첫 적재 대상은 PostgreSQL로 시작 |
| ERD 검토 | 23개 테이블의 확장 모델 작성 | 초기 4개 테이블만 이번 SQL에 반영 |
| Docker 구성 | 실행 환경 공유·데이터 유지·백업 검토 | Compose + 외부 Named volume + 복구 검증 |

위 표는 노션 기록의 요약이며, 모든 후보 설계가 구현됐다는 의미는 아님.

## 이번 구현의 선택

**초기 범위 — 4개 테이블**

| 테이블 | 한 행의 의미 | 주요 연결·제약 |
|---|---|---|
| company | 확인한 법인 또는 조직 하나 | 내부 UUID로 연결, 기업명만으로 자동 병합 금지 |
| company_identifier | 특정 체계의 외부 기업 식별자 하나 | company FK, namespace + external_value 중복 방지 |
| product | 제품·서비스 하나 | 현재 확인한 운영 기업 company_id 연결 |
| financial_observation | 출처·개정·항목·추출 버전이 특정된 재무 값 하나 | company FK, 기간·통화·연결/별도 기준 보존 |

이 범위는 초기 구현 대상으로 직접 선택한 기업·식별자·제품·재무 기준. 원문 테이블의 FK는 출처 URL·수집 시점으로 대체하고, 재무에는 원문 파일 경로와 개정 식별자를 추가. 원문 모델 도입 시 해당 필드를 문서 FK로 이관하는 마이그레이션 필요.

**PostgreSQL — 관계와 제약조건부터 검증**

현재 조회·저장 단위는 기업에 연결된 구조화 데이터. FK·고유 제약·트랜잭션을 활용해 기업 연결과 중복 처리를 먼저 검증하는 선택. 검색 품질이나 관계 탐색 성능을 측정하지 않은 단계이므로, Vector·Search·Graph의 필요성은 아직 결론을 내리지 않은 상태.

**별도 볼륨 — 실행 환경과 데이터의 분리**

컨테이너 재생성 시 같은 DB 볼륨 재사용. `external: true`로 Compose 수명과 분리하되, 삭제·손상 복구는 pg_dump 백업으로 대비. SQL 파일은 Git, 원문과 백업은 별도 보관.

**변경 이력 — 보존 가능한 범위의 명시**

- 기업·제품: 현재 값 저장, UPDATE 전 값 자동 보존은 미지원
- 재무: 정정 시 새 source_revision으로 INSERT, 동일 개정 재처리는 고유 제약으로 중복 방지
- 원문: 재무 raw_uri가 가리키는 스냅샷 파일 별도 보관
- 감사: DB 관리자의 UPDATE·DELETE를 차단하는 불변 감사 로그는 미구현
- 조회: 정정·출처 충돌을 고려한 최신 유효 값 선택 규칙은 수집기 구현 시 확정

## 다른 설계안과의 관계

노션의 `1차 DB 스키마 설계`에는 원문 → 정제 문서 → 파생 데이터 중심의 공통 구조도 존재. 이 안은 재무를 후속 도메인으로 두므로 이번 4개 테이블과 동일한 설계가 아님.

이번 PR은 4개 테이블을 검증할 첫 구현. 공통 원문 구조는 검토안으로 유지. 향후 다중 출처 재파싱·문서 이력·검색이 필요해지는 시점에 두 모델의 통합 비용과 이점을 비교. 동료의 원문 조사 문서는 별도 기록으로 유지.
